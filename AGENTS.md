# Agent Instructions — tinyllm

## Overview

When implementing SystemVerilog cores, adhere to the `description.yaml` in that
core's `src/` directory. The `llm_guidance` field tells you what to implement;
the `description` field tells you what the unit does and its tensor/parameter
details.

## Current DUT

Each session must declare the unit currently under development in the
`description.yaml` of that unit. Before starting work, set:

```yaml
current_dut: <unit_name>
```

This tells all agents which unit is actively being implemented and tested.
Only one unit should be `current_dut` at a time. When work on a unit is
complete, clear the field before starting the next unit.

Refer to `LLM_LAYER_DESCRIPTION.md` — "Operations Needed for SystemVerilog
Implementation" section — for the dependency-ordered list of units. Implement
in order from Layer 1 (leaf operations) upward.

## Open-Source Toolchain

The `oss-cad-suite/` directory at the project root provides all required tools.
Activate it before running any tool:

```bash
source /path/to/tinyllm/oss-cad-suite/environment
```

| Tool | Purpose | Command |
|------|---------|---------|
| **Yosys** | Synthesis, linting | `yosys -p "read_verilog -lint *.sv"` |
| **Verilator** | RTL simulation, linting | `verilator --lint-only -Wall *.sv` |
| **SymbiYosys (sby)** | Formal property verification | `sby -f config.sby` |
| **cocotb** | Python-driven RTL testbenches | `cocotb-config` / `uv run cocotb` |

### Linting

Run Verilator lint on every `.sv` file before simulation:

```bash
verilator --lint-only -Wall src/<unit>/<unit>.sv
```

Fix all warnings. A clean lint pass is required before formal or simulation.

### Formal Verification

Use SymbiYosys for bounded model checking (BMC) of key properties.
Create a `properties.sv` file with `assert` statements and a `.sby` config.
Run with `sby -f <config>.sby`.

### Functional Equivalence — cocotb

All functional testing uses **cocotb** with Verilator as the simulator.
Tests run in a loop against a **golden sample** generated by the Python
reference implementation.

**Test structure per unit:**

```
src/<unit>/
  <unit>.sv              # RTL implementation
  tb_<unit>.py           # cocotb testbench
  Makefile               # cocotb runner config
```

**Testing workflow:**

1. Generate golden sample data from the Python function (use the model's
   Python implementation or a standalone reference script).
2. Write a cocotb test that feeds the same inputs to the RTL and compares
   outputs against the golden sample.
3. Run the test in a loop (multiple input vectors) to build confidence.
4. Use the existing FPU test suite (`systemverilog_fp_unit/tests/`) as a
   reference for cocotb test patterns.

### In-Loop Verification

After unit-level cocotb tests pass, verify the unit **in-loop** by integrating
it into the full data flow and running it in parallel with the Python golden
reference. This confirms the unit works correctly when driven by real model
data and its output feeds back into the downstream system.

**In-loop test structure:**

```
src/<unit>/
  tb_<unit>_inloop.py    # in-loop cocotb testbench
```

**In-loop testing workflow:**

1. Load the Python model and run a forward pass with `torch.no_grad()`.
2. Hook into the target layer to capture its real input activations.
3. Feed those activations through the DUT in RTL simulation.
4. Capture the DUT output and compare against the Python layer's output.
5. Run this in a loop over multiple sequence positions or batches.
6. The Python reference and RTL simulation run **in parallel** — the same
   input vectors go to both, and outputs are compared after each vector.

**Key difference from unit tests:** Unit tests use synthetic/random inputs.
In-loop tests use **real model activations** extracted from the actual
Granite 4.0-H-350M forward pass, verifying the unit in its true operating
context.

## Working on a Unit — Step by Step

When starting work on a unit, first create a `TODO.md` in that unit's `src/<unit>/`
directory. Copy the code review checklist below into it and use it to track progress.
Update the TODO.md as you complete each step.

1. **Read `description.yaml`** — understand the unit's purpose, tensor shapes,
   and the `llm_guidance` instructions.

2. **Implement the RTL** — write `<unit>.sv` following the description.

3. **Lint** — run `verilator --lint-only -Wall` and fix all issues.

4. **Write cocotb testbench** — create `tb_<unit>.py` that:
   - Loads the unit under test.
   - Generates or loads golden sample data from the Python reference.
   - Drives inputs and compares outputs cycle-by-cycle.
   - Runs in a loop over multiple test vectors.

5. **Run RTL simulation** — execute the cocotb test against Verilator.
   Verify functional equivalence against the golden sample.

6. **In-loop verification** — integrate the unit into the data flow and run
   it in parallel with the Python golden reference. Feed real model activations
   through the DUT and compare outputs against the Python layer's output.
   This confirms the unit works in its true operating context.

7. **Update `description.yaml`** — once the unit is working, fill in:
   - `interface:` — port list with directions and widths.
   - `max_clock_speed:` — the maximum Fmax determined from timing analysis
     or Verilator clock period testing.
   - `characteristics:` — latency, throughput, resource usage, any
     operational notes discovered during implementation.

8. **Formal verification** (if applicable) — write properties and run sby.

## Golden Sample Generation

The Python reference is the source of truth. To generate golden samples:

- Use the model's Python implementation from `transformers` (loaded in
  `tests/test_granite_inference.py`).
- Extract intermediate activations by running the model with `torch.no_grad()`
  and hooking into the relevant layer.
- Save inputs/outputs as hex or binary files for the cocotb testbench to read.

Example pattern:

```python
import torch
from transformers import AutoModelForCausalLM

model = AutoModelForCausalLM.from_pretrained("granite-4.0-h-350m", dtype=torch.bfloat16)
# Hook into the target layer, capture inputs/outputs, save to file.
```

## Code Review Checklist

Before marking a unit complete:

- [ ] RTL passes Verilator lint with `-Wall` (no warnings).
- [ ] cocotb testbench passes against golden sample for all test vectors.
- [ ] In-loop test passes — DUT output matches Python layer output with real model data.
- [ ] `description.yaml` is updated with interface, Fmax, and characteristics.
- [ ] No hardcoded magic numbers — use parameters or `define` constants.
- [ ] Follows existing code conventions (see `systemverilog_fp_unit/rtl/`).
